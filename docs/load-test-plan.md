# 콘서트 예약 시스템 부하 테스트 계획서

> **작성 목적**: 부하 테스트 대상 선정, 목적, 시나리오 계획 및 인프라/시간 확보를 위한 상사 보고용 문서

## 1. Executive Summary

콘서트 예약 서비스는 **콘서트 오픈 직후** 및 **매진 시점**에 트래픽이 극단적으로 집중되는 특성이 있습니다. 실제 서비스 장애를 방지하고, 적절한 배포 스펙을 산정하기 위해 **부하 테스트**를 수행할 필요가 있습니다.

본 문서에서는 부하 테스트 대상, 목적, 시나리오, 필요 인프라 및 소요 시간을 정리하여 검토 요청드립니다.

## 2. 부하 테스트 대상 선정

### 2.1 어떤 부분을 부하 테스트해야 할까?

| 우선순위 | API | Method | 경로 | 선정 이유 |
|----------|-----|--------|------|-----------|
| **1** | 좌석 예약(홀드) | POST | `/api/v1/reservation/dates/place` | Redis 분산락 + DB 락 + 트랜잭션으로 **동시성 병목** 가능성 최고. 콘서트 오픈 시 최대 트래픽 집중 |
| **2** | 결제 처리 | POST | `/api/v1/reservation/{id}/payment` | 지갑 차감, Ledger 기록, 예약 상태 변경 등 **복합 트랜잭션**. 예약 직후 결제 요청 집중 |
| **3** | 랭킹 조회 | GET | `/api/v1/ranking/soldout` | 매진 직후 **조회 트래픽 폭증**. Redis Sorted Set 조회 부하 |
| **4** | 예약 가능 일정 조회 | GET | `/api/v1/reservation/possibility/{id}/dates` | 콘서트 선택 시 **빈번한 조회**. DB 조인 쿼리 부하 |

### 2.2 왜 이 부분을 부하 테스트해야 할까?

| 구분 | 설명 |
|------|------|
| **비즈니스 리스크** | 예약/결제 실패 시 매출 손실 및 고객 이탈. 랭킹 조회 지연 시 UX 저하 |
| **기술적 병목** | Redis 락 경합, DB 커넥션 풀 고갈, HikariCP/ThreadPool 한계 |
| **실제 트래픽 패턴** | kafka-design.md 5.1절: "콘서트 오픈 직후", "인기 콘서트 매진 시점"에 트래픽 집중 |
| **배포 스펙 산정** | CPU/Memory 제한 시 성능 한계 파악 → 적정 배포 스펙 도출 |

## 3. 부하 테스트 목적

| 목적 | 세부 내용 |
|------|------------|
| **성능 한계 파악** | 동시 사용자 수(CCU) 증가 시 응답 시간, TPS, 에러율 변화 측정 |
| **적정 배포 스펙 산정** | Docker CPU/Memory 제한을 조절하며 목표 SLA(예: p95 < 500ms) 달성 가능 스펙 도출 |
| **병목 구간 식별** | DB, Redis, 애플리케이션 중 어디서 성능이 저하되는지 파악 |
| **안정성 검증** | 부하 지속 시 메모리 누수, 커넥션 누수 등 장애 징후 확인 |

## 4. 부하 테스트 시나리오

### 4.1 시나리오 1: 좌석 예약(홀드) 부하 테스트

- **대상**: `POST /api/v1/reservation/dates/place`
- **시나리오**: 동시 50~200명이 동일 콘서트 일정의 좌석을 선점 시도
- **목표**: p95 응답 시간 < 1초, 에러율 < 1%
- **예상 병목**: Redis 분산락 경합, DB `SELECT FOR UPDATE` 대기

### 4.2 시나리오 2: 결제 처리 부하 테스트

- **대상**: `POST /api/v1/reservation/{reservationId}/payment`
- **시나리오**: 예약 완료 후 30초 내 결제 요청 집중 (50~100 CCU)
- **목표**: p95 응답 시간 < 2초, 에러율 0%
- **예상 병목**: DB 트랜잭션, HikariCP 커넥션 풀

### 4.3 시나리오 3: 랭킹 조회 부하 테스트

- **대상**: `GET /api/v1/ranking/soldout`
- **시나리오**: 매진 직후 100~500 CCU가 동시 조회
- **목표**: p95 응답 시간 < 200ms, 에러율 0%
- **예상 병목**: Redis ZRANGE 조회

### 4.4 시나리오 4: 시나리오 통합 (예약 → 결제 → 랭킹)

- **흐름**: 예약 가능 일정 조회 → 좌석 예약 → 결제 → 랭킹 조회
- **목적**: 실제 사용자 행동 패턴 시뮬레이션
- **부하**: Ramp-up 0→100 CCU 30초, 유지 60초, Ramp-down 30초

## 5. 부하 테스트 방법

### 5.1 도구

| 도구 | 용도 | 선택 이유 |
|------|------|-----------|
| **k6** | HTTP 부하 테스트 스크립트 작성 및 실행 | JavaScript 기반, 가벼움, CLI/CI 친화적, 상세 메트릭 출력 |

### 5.2 실행 환경

- **애플리케이션**: Docker 컨테이너 (CPU/Memory 제한 적용)
- **인프라**: MySQL, Redis (docker-compose)
- **부하 생성**: k6 로컬 실행 또는 별도 컨테이너

### 5.3 리소스 제한 실험

| 실험 | CPU | Memory | 목적 |
|------|-----|--------|------|
| Low | 0.5 core | 512MB | 최소 스펙에서 성능 한계 |
| Medium | 1 core | 1GB | 기본 권장 스펙 |
| High | 2 core | 2GB | 여유 스펙 |

## 6. 필요 인프라 및 시간

### 6.1 인프라 요청

| 항목 | 내용 |
|------|------|
| **테스트 환경** | 개발/스테이징 서버 또는 로컬 Docker 환경 (MySQL, Redis 포함) |
| **부하 생성기** | k6 설치 가능한 PC 또는 CI Runner (최소 4코어 권장) |
| **네트워크** | 애플리케이션과 부하 생성기 간 낮은 지연 (동일 VPC 또는 로컬) |

### 6.2 소요 시간

| 단계 | 소요 시간 | 내용 |
|------|-----------|------|
| 테스트 데이터 준비 | 0.5일 | 콘서트, 좌석, 사용자 시드 데이터 |
| 스크립트 작성 | 1일 | k6 시나리오 작성 및 검증 |
| 부하 테스트 실행 | 1일 | 시나리오별 실행, 리소스 제한 실험 |
| 결과 분석 및 보고 | 0.5일 | 메트릭 정리, 배포 스펙 권장안 작성 |
| **합계** | **약 3일** | |

### 6.3 기대 효과

- **배포 비용 최적화**: 과도한 스펙 방지, 최소 스펙으로 목표 SLA 달성
- **장애 예방**: 실제 트래픽 전 병목 구간 사전 파악
- **운영 지표**: 목표 TPS, CCU 기준치 수립
